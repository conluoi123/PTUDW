# 🌐 Google Cloud Platform (GCP) Deployment Guide

This guide provides step-by-step instructions for deploying the **WEBGAME** application (comprising a Node.js/Express backend and a React/Vite frontend) to Google Cloud Platform (GCP) while keeping the database hosted on Supabase (or migrating to Cloud SQL).

---

## 🏗️ Recommended GCP Architecture

For a scalable, cost-efficient, and secure architecture, we recommend the following GCP services:

| Component | GCP Service | Rationale | Cost |
|---|---|---|---|
| **Backend API** | **Google Cloud Run** | Serverless container hosting. Scales to zero when not in use. Handles HTTPS automatically. | Extremely Low (Free tier available) |
| **Frontend Web** | **Firebase Hosting** *or*<br>**GCS + Load Balancer + CDN** | Firebase Hosting is the easiest way to host React SPAs (runs on GCP edge CDN). Cloud Storage is more native but requires load balancer setup. | Extremely Low / Free |
| **Database** | **Supabase (Existing)** *or*<br>**GCP Cloud SQL (PostgreSQL)** | Keep Supabase to save costs and avoid migration effort. Or migrate to Cloud SQL (fully-managed Postgres on GCP) if required. | Supabase: Free<br>Cloud SQL: ~$10-30+/mo |
| **Secrets Management**| **Google Secret Manager** | Secures backend sensitive keys (JWT, DB passwords, OAuth keys). | Free Tier / Fractional cents |

## 🔑 Environment Variables Mapping

Before starting, review the environment variables that need to be populated.

### 1. Backend Service Configuration (Cloud Run)
Cloud Run injects the `PORT` env variable automatically (typically `8080`). You must configure the remaining variables in the Cloud Run service environment settings or via Google Secret Manager.

| Variable Name | Required? | Source / Description | Suggested Value in Production |
|---|---|---|---|
| `PORT` | Yes | Injected by Cloud Run automatically. | `8080` (managed by Cloud Run) |
| `DB_PASSWORD` | Yes | Database password for connection. | Your Supabase database password |
| `JWT_SECRET` | Yes | Secret key used to sign access tokens. | A strong random string (e.g., generated by `openssl rand -hex 32`) |
| `SESSION_SECRET` | Yes | Secret key used to sign Express sessions. | A strong random string |
| `FRONTEND_URL` | Yes | URL where your frontend is hosted. | `https://your-frontend-domain.web.app` (or GCS Load Balancer URL) |
| `BACKEND_URL` | Yes | URL where the Cloud Run API is hosted. | `https://webgame-backend-xxxxx-an.a.run.app` (generated by Cloud Run) |
| `X_API_KEY` | No | Security key for API verification. | Optional, leave empty if not used |
| **Google OAuth** | | | |
| `GOOGLE_LOGIN_URL` | No | Google Auth authorization URL. | `https://accounts.google.com/o/oauth2/v2/auth` |
| `GOOGLE_REDIRECT_URL`| No | Redirect callback route. | `/api/user/login/google/callback` |
| `GOOGLE_CLIENT_ID` | No | OAuth Client ID from Google Cloud Console. | `your-google-oauth-client-id.apps.googleusercontent.com` |
| `GOOGLE_SECRET_ID` | No | OAuth Client Secret from Google Cloud Console. | `your-google-oauth-client-secret` |
| **Cloudinary** | | | |
| `CLOUDINARY_NAME` | No | Cloudinary name for image hosting. | Your Cloudinary Cloud Name |
| `CLOUDINARY_API_KEY` | No | Cloudinary API Key. | Your Cloudinary API Key |
| `CLOUDINARY_SECRET_KEY`| No | Cloudinary API Secret. | Your Cloudinary Secret |

### 2. Frontend Configuration (React Build)
Vite loads environment variables at **build-time**. Thus, you must set this variable in your local terminal or CI/CD environment *before* running the build command.

| Variable Name | Required? | Description | Suggested Value in Production |
|---|---|---|---|
| `VITE_API_URL` | Yes | Absolute URL of the backend API server. | `https://webgame-backend-xxxxx-an.a.run.app` (Must be the deployed Cloud Run service URL) |

## 🛠️ Step-by-Step Deployment Instructions

### Prerequisite: Setup Google Cloud SDK
1. Download and install the [Google Cloud SDK (gcloud CLI)](https://cloud.google.com/sdk/docs/install).
2. Initialize and authenticate the CLI:
   ```bash
   gcloud init
   gcloud auth login
   ```
3. Set your active project:
   ```bash
   gcloud config set project <YOUR_GCP_PROJECT_ID>
   ```
4. Enable the necessary APIs:
   ```bash
   gcloud services enable run.googleapis.com \
                          artifactregistry.googleapis.com \
                          cloudbuild.googleapis.com \
                          secretmanager.googleapis.com
   ```

---

### Phase 1: Deploy Backend to Google Cloud Run

We have already created a production-ready [Dockerfile](file:///d:/CNTT/2025-2026/hk1/Web/personal_project/PTUDW/backend/Dockerfile) and [.dockerignore](file:///d:/CNTT/2025-2026/hk1/Web/personal_project/PTUDW/backend/.dockerignore) inside your `backend` directory.

#### Step 1.1: Build and Submit the Container Image to GCP
We will use **Google Cloud Build** to build the Docker image in the cloud and store it in **Artifact Registry**.

1. Create an Artifact Registry repository (if you don't have one):
   ```bash
   gcloud artifacts repositories create webgame-repo \
       --repository-format=docker \
       --location=asia-northeast2 \
       --description="Docker repository for Webgame"
   ```
2. Navigate to your backend directory and trigger the build:
   ```bash
   cd backend
   gcloud builds submit --tag asia-northeast2-docker.pkg.dev/<YOUR_GCP_PROJECT_ID>/webgame-repo/backend-service:latest
   ```

#### Step 1.2: Deploy to Cloud Run
Deploy the built image to Cloud Run. Keep note of the generated **Service URL** output by this command (you will need it for the frontend environment configuration).

```bash
gcloud run deploy webgame-backend \
    --image=asia-northeast2-docker.pkg.dev/<YOUR_GCP_PROJECT_ID>/webgame-repo/backend-service:latest \
    --region=asia-northeast2 \
    --platform=managed \
    --allow-unauthenticated \
    --set-env-vars="DB_PASSWORD=<your_db_password>,JWT_SECRET=<your_jwt_secret>,SESSION_SECRET=<your_session_secret>,GOOGLE_CLIENT_ID=<google_client_id>,GOOGLE_SECRET_ID=<google_secret>,CLOUDINARY_NAME=<cloud_name>,CLOUDINARY_API_KEY=<key>,CLOUDINARY_SECRET_KEY=<secret>"
```

> [!TIP]
> **Production Best Practice (Google Secret Manager):**
> Instead of passing raw credentials via `--set-env-vars`, store them securely in Secret Manager and map them using:
> `--set-secrets="DB_PASSWORD=DB_PASSWORD:latest,JWT_SECRET=JWT_SECRET:latest"`

---

### Phase 2: Run Database Migrations

Since the database is hosted on Supabase, the easiest way to run migrations is from your local machine targeting the Supabase database instance.

1. Ensure your local `backend/.env` is temporarily configured with the correct `DB_PASSWORD`.
2. Run the Knex migrations from the backend directory:
   ```bash
   cd backend
   npm install
   npm run migrate
   ```
   *(Optional: Use `npm run seed` to populate initial game directories and data).*

---

### Phase 3: Build and Deploy the React Frontend

The React application must be built statically and pointing to the live backend URL.

#### Step 3.1: Build Frontend Assets
1. Navigate to the frontend directory:
   ```bash
   cd ../frontend
   ```
2. Create or update `frontend/.env` with your live Backend URL:
   ```env
   VITE_API_URL=https://webgame-backend-xxxxx-an.a.run.app
   ```
   *(Replace with the actual URL provided by the `gcloud run deploy` command in Phase 1).*
3. Install dependencies and compile the production build:
   ```bash
   npm install
   npm run build
   ```
   This will generate a static production folder called `dist/`.

#### Step 3.2: Option A - Deploy using Firebase Hosting (Recommended)
Firebase Hosting is a GCP-aligned service that is fast, cheap, and offers simple deployments.

1. Install the Firebase CLI:
   ```bash
   npm install -g firebase-tools
   ```
2. Log in and initialize:
   ```bash
   firebase login
   firebase init hosting
   ```
   *   Select your GCP Project.
   *   Set the public directory to **`dist`** (Vite's build output).
   *   Configure as a single-page app: **`Yes`**.
   *   Overwrite `index.html`: **`No`**.
3. Deploy the application:
   ```bash
   firebase deploy --only hosting
   ```
4. Copy the hosting URL (e.g. `https://your-project.web.app`).

#### Step 3.2: Option B - Deploy to Google Cloud Storage (GCS)
If you prefer native GCP bucket hosting:

1. Create a public Cloud Storage bucket:
   ```bash
   gsutil mb -c standard -l asia-northeast2 gs://your-webgame-bucket/
   ```
2. Configure website configuration:
   ```bash
   gsutil web set -m index.html -e index.html gs://your-webgame-bucket/
   ```
3. Upload the build files:
   ```bash
   gsutil -m rsync -R dist/ gs://your-webgame-bucket/
   ```
4. Make all objects publicly readable:
   ```bash
   gsutil iam ch allUsers:objectViewer gs://your-webgame-bucket/
   ```
5. *(Optional)* Set up an HTTPS Load Balancer with Cloud CDN pointing to the bucket backend to serve traffic securely over HTTPS.

---

### Phase 4: Finalize Configurations (CORS & Redirects)

Once the frontend URL is deployed (e.g., `https://your-project.web.app`), you must update the CORS configuration in the backend Cloud Run service.

1. Update the backend Cloud Run environment variables to authorize the frontend URL:
   ```bash
   gcloud run services update webgame-backend \
       --region=asia-northeast2 \
       --update-env-vars="FRONTEND_URL=https://your-project.web.app,BACKEND_URL=https://webgame-backend-xxxxx-an.a.run.app"
   ```

2. If using **Google OAuth**, go to [Google Cloud Console API Credentials](https://console.cloud.google.com/apis/credentials):
   *   Under **Authorized JavaScript origins**, add your frontend URL: `https://your-project.web.app`.
   *   Under **Authorized redirect URIs**, add your backend callback URL: `https://webgame-backend-xxxxx-an.a.run.app/api/user/login/google/callback`.

## 🔒 Security Recommendations for GCP

1. **Service Accounts**: Do not run Cloud Run under the default Compute Engine Service Account. Create a custom service account with minimal IAM roles (e.g., only Secret Manager Secret Accessor, if secrets are used).
2. **CORS policies**: Ensure `FRONTEND_URL` exactly matches the URL of your frontend to prevent Cross-Origin resource leaks.
3. **Database Security**: Supabase connections are secured via SSL (`ssl: { rejectUnauthorized: false }` is enabled in `knexfile.js`). If you migrate to GCP Cloud SQL, use the **Cloud SQL Auth Proxy** in Cloud Run configurations for secure, password-less connections using IAM credentials.

## ⚠️ Phase 0: Critical Pre-Deployment Decisions

Before executing Phases 1–4, you must resolve the two key issues below. **These block a working production deployment.**

---

### 🔐 Issue 1: Google OAuth2 — Migrating from Localhost to Production URIs

Currently your `.env` and Google Cloud Console OAuth credential are configured with `localhost` origins and redirect URIs. This **will not work** in production. The Google OAuth flow requires that the redirect URL returned by your server exactly matches a URI registered in the Cloud Console.

#### What needs to change:

**In Google Cloud Console → APIs & Services → Credentials → Your OAuth 2.0 Client ID:**

| Setting | Current (Dev) | Required (Production) |
|---|---|---|
| **Authorized JavaScript origins** | `http://localhost:5173` | `https://your-project.web.app` *(your Firebase Hosting URL)* |
| **Authorized redirect URIs** | `http://localhost:3000/api/user/login/google/callback` | `https://webgame-backend-xxxxx-an.a.run.app/api/user/login/google/callback` |

**In your backend `.env` / Cloud Run environment variables:**

| Variable | Current (Dev) | Required (Production) |
|---|---|---|
| `BACKEND_URL` | `http://localhost:3000` | `https://webgame-backend-xxxxx-an.a.run.app` |
| `FRONTEND_URL` | `http://localhost:5173` | `https://your-project.web.app` |
| `GOOGLE_REDIRECT_URL` | `/api/user/login/google/callback` *(relative path — OK if your server prepends `BACKEND_URL`)* | Same relative path — **verify your backend constructs the full callback URL using `BACKEND_URL` + `GOOGLE_REDIRECT_URL`** |

#### Step-by-step action:

1. **Deploy the backend first** (Phase 1) to get the Cloud Run URL.
2. **Deploy the frontend** (Phase 3) to get the Firebase Hosting URL.
3. Go to [Google Cloud Console → Credentials](https://console.cloud.google.com/apis/credentials).
4. Click your OAuth 2.0 Client ID → **Edit**.
5. Under **Authorized JavaScript origins** → Add `https://your-project.web.app`.
6. Under **Authorized redirect URIs** → Add `https://webgame-backend-xxxxx-an.a.run.app/api/user/login/google/callback`.
7. Click **Save** (changes can take up to 5 minutes to propagate).
8. Update Cloud Run env vars (Phase 4 Step 1) with the correct `FRONTEND_URL` and `BACKEND_URL`.

> [!CAUTION]
> Do NOT remove the `localhost` entries from the OAuth credential during development/testing. You can keep both localhost and production URIs registered simultaneously in the same OAuth credential.

### 🐳 Issue 2: Port Differences — Docker (Cloud Run) vs Local Node.js Dev

This is a critical source of confusion. Here is a complete breakdown:

#### Port Mapping Table

| Context | Who listens | Port inside container | Port you access | Notes |
|---|---|---|---|---|
| **Local: `npm run dev`** | Node.js directly on host | — | `3000` | No Docker. `PORT=3000` in `.env`. |
| **Local: `docker-compose up`** | Docker container | `8080` (inside) | `3000` (host) | `docker-compose.yml`: `"3000:8080"` maps host→container |
| **GCP Cloud Run** | Docker container | `8080` (required) | `443` / HTTPS (public) | Cloud Run auto-injects `PORT=8080` and provides HTTPS URL |

#### Key Differences Explained

```
Local Node.js dev:
  Your Code (PORT=3000) ──────────────────────► http://localhost:3000

Local Docker (docker-compose):
  Host:3000 ──► Container:8080 ──► Your Code (PORT=8080)
  (port mapping "3000:8080" in docker-compose.yml)
  You access: http://localhost:3000 (same as before, but Docker handles it)

GCP Cloud Run:
  Internet:443 (HTTPS) ──► Cloud Run Proxy ──► Container:8080 ──► Your Code (PORT=8080)
  You access: https://webgame-backend-xxxxx-an.a.run.app  (no port in URL!)
```

#### What your code must do correctly

Your `backend/index.js` (or `app.js`) should use:
```js
const PORT = process.env.PORT || 3000;
app.listen(PORT, () => console.log(`Server running on port ${PORT}`));
```
- **Locally (npm run dev):** `PORT=3000` from `.env` → listens on 3000 ✅
- **Docker / Cloud Run:** `PORT=8080` injected by Docker/Cloud Run → listens on 8080 ✅
- **You never hardcode the port** → same code works everywhere ✅

#### What `GOOGLE_REDIRECT_URL` / OAuth callback must use

| Context | Correct callback URL to register in Google Console |
|---|---|
| Local dev (`npm run dev`) | `http://localhost:3000/api/user/login/google/callback` |
| Local Docker (`docker-compose`) | `http://localhost:3000/api/user/login/google/callback` *(still port 3000, the host-mapped port)* |
| Cloud Run (production) | `https://webgame-backend-xxxxx-an.a.run.app/api/user/login/google/callback` *(no port — Cloud Run handles HTTPS on 443)* |

> [!IMPORTANT]
> Cloud Run exposes your app over **HTTPS on port 443** automatically. The internal container port is always `8080`, but users never see it. Your OAuth redirect URI in Google Console must use the public `https://...run.app` URL with **no port number**.

#### Summary of what to change before deploying

- [ ] Confirm `const PORT = process.env.PORT || 3000` is used in `backend/index.js`
- [ ] Do NOT hardcode `3000` anywhere in the OAuth callback construction
- [ ] Add production URLs to Google OAuth Console (Step 6 above)
- [ ] Set `BACKEND_URL` and `FRONTEND_URL` env vars in Cloud Run to `https://...` URLs (no port)
- [ ] Set `VITE_API_URL` in frontend build to `https://webgame-backend-xxxxx-an.a.run.app` (no port)
